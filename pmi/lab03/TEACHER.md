## Как сервис оценивает историю

Сервис скачивает репозиторий **с полной историей и тегами**. Собственными считаются коммиты,
которых нет в репозитории курса.

| Критерий | Что проверяется |
|---|---|
| Состояния проекта | не меньше восьми собственных коммитов; коммиты слияния тоже считаются |
| Сообщения | не меньше 80% осмысленны; «update», «fix», «1» не считаются, слияния не учитываются |
| Отмена | есть коммит, сообщение которого начинается с `Revert` — его создаёт `git revert` |
| Ветвление | есть коммит слияния (два родителя): ветка влита с `--no-ff` |
| Тег | есть тег, указывающий на **собственный** коммит студента; годится и лёгкий, и аннотированный |
| NOTES.md | в тексте есть `diff`, `log`, `restore` (или `checkout`), `revert`, «тег» и «ветк» |

Ожидаемая история — примерно так:

```
*   Merge branch experiment
|\
| * Add safe division
|/
* Разобрал отличие revert от reset      ← v1.0 может стоять здесь или ниже
* Revert "Add division"
* Add division
* Описал восстановление файлов
* Описал diff, show и log
* Add multiplication
* Add subtraction
* Add sum calculation
```

Смысл записей автоматика не оценивает: слово «restore» в тексте ещё не значит, что студент
понимает, что оно делает. Это — защита.

## Как проверять

1. Откройте попытку. Раздел **«Работа с Git»** показывает собственные коммиты, теги,
   коммиты отмены и слияния. Список коммитов — в «Технических подробностях».
2. На защите дайте **живую задачу**: испортить файл и вернуть его, затем отменить последний
   коммит. Смотрите, лезет ли студент в `reset --hard` там, где нужен `revert`.
3. Спросите про `NOTES.md`: пусть объяснит своими словами, чем `git restore <файл>` отличается
   от `git restore --source=...`.
4. Задайте вопросы из банка и поставьте 0–2 за защиту.

## Типичные проблемы

| Симптом в сервисе | Причина | Что сказать студенту |
|---|---|---|
| «тегов 0», хотя тег стоит | тег не отправлен: обычный `push` теги не шлёт | `git push origin v1.0` |
| тег есть, но не засчитан | тег поставлен на коммит репозитория курса или на чужой коммит | поставить тег на свой коммит |
| «коммитов отмены: 0» | вместо `revert` сделан `reset --hard` или правка руками | история переписана; на защите — разобрать, чем это опасно |
| «слияний в истории нет» | ветку слили без `--no-ff` (fast-forward) или не слили вовсе | ещё одна ветка с правкой и `git merge --no-ff` |
| собственных коммитов меньше восьми | шаги воркшопа свалены в один-два коммита | каждый шаг — отдельный коммит; засчитывается то, что в истории |
| NOTES.md засчитан частично | разобраны не все шесть тем | сервис называет, каких понятий не хватает |
| ошибочного коммита нет вовсе | студент сразу написал деление с проверкой нуля | по условию ошибку нужно закоммитить, иначе нечего отменять |

## Вопросы для защиты

Видны только преподавателям. В сервисе — вкладка «Вопросы защиты» у практики и форма проверки попытки.
Базовые задайте каждому — два-три на выбор; сложные — если базовые даются легко или есть сомнения в авторстве.

### Базовые

**1. Что сравнивают git diff, git show и git log -p?** · _Сравнение версий_

> diff — два состояния (рабочую копию с индексом или два коммита), show — один коммит с его изменениями, log -p — всю историю с изменениями каждого коммита.

**2. Файл испорчен, но не закоммичен. Как вернуть его и что при этом потеряется?** · _Восстановление_

> git restore <файл> возьмёт версию из последнего коммита. Несохранённые правки в этом файле пропадут — Git о них не знал.

**3. Чем git restore <файл> отличается от git restore --source=HEAD~2 <файл>?** · _Восстановление_

> Первый берёт версию из последнего коммита, второй — из указанного. Во втором случае в рабочей папке окажется старая версия, и её можно закоммитить как новую.

**4. Чем revert отличается от reset --hard?** · _Отмена изменений_

> revert создаёт новый коммит, отменяющий изменения: история сохраняется. reset --hard сдвигает ветку назад и выбрасывает коммиты — в опубликованной истории это опасно.

**5. Почему после revert в истории стало на два коммита больше, а не на ноль?** · _Отмена изменений_

> Ошибочный коммит остался на месте, к нему добавился коммит отмены. Так видно и ошибку, и её исправление.

**6. Что такое тег и чем он отличается от ветки?** · _Теги_

> Тег — постоянное имя коммита, он не двигается. Ветка — указатель, который передвигается при каждом новом коммите.

**7. Почему тег не появился на GitHub после обычного git push?** · _Теги_

> push отправляет коммиты ветки, а теги — нет. Нужен git push origin v1.0 или git push --tags.

**8. Зачем эксперимент делать в отдельной ветке, а не в main?** · _Ветки_

> Неудачную ветку можно просто удалить, и main останется рабочей. В main пришлось бы отменять коммиты.

**9. Покажите по git log --oneline --graph, где в вашей истории отмена и где слияние.** · _История_

> Коммит Revert … отменяет ошибочный коммит, коммит слияния соединяет ветку experiment с main и имеет двух родителей.

**10. Что показывает git blame и когда это нужно?** · _Поиск изменений_

> Для каждой строки файла — коммит и автора, которые её добавили. Нужно, чтобы понять, откуда взялась строка и зачем её меняли.

### Сложные

**11. Как найти коммит, в котором появилась или исчезла конкретная строка?** · _Поиск изменений_

> git log -S"текст" -- <файл>: покажет коммиты, изменившие число вхождений этой строки.

**12. Можно ли отменить коммит слияния через revert?** · _Отмена изменений_

> Можно, но нужно указать, какого родителя считать основным: git revert -m 1 <sha>. Без -m Git не знает, к какой линии возвращаться.

**13. Чем аннотированный тег (-a) отличается от лёгкого?** · _Теги_

> Аннотированный — отдельный объект с автором, датой и сообщением; лёгкий — просто имя коммита. Для версий используют аннотированный.

**14. Вы удалили ветку после слияния. Как найти её коммиты потом?** · _Ветки_

> Они входят в историю main: git log --oneline --graph покажет их линией слияния. Имя ветки при этом не нужно.
