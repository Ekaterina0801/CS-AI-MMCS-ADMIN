## Как сервис оценивает историю

Сервис скачивает fork студента **с полной историей** и подключает вторым источником репозиторий курса
[CS-AI-MMCS](https://github.com/Ekaterina0801/CS-AI-MMCS). Коммиты, которых нет в ветке `main` курса, считаются собственными.
Поэтому коммиты преподавателя, полученные при форке или через Sync fork, в три обязательных не входят.

| Критерий | Что проверяется |
|---|---|
| Три собственных коммита | число коммитов, отсутствующих в репозитории курса |
| Объяснения в `NOTES.md` | в тексте есть рабочая папка, индекс (или staging), коммит и GitHub |
| Сообщения коммитов | не меньше 80% сообщений осмысленны: «update», «fix», «1» не считаются |
| Публикация в fork | собственные коммиты есть в опубликованном репозитории |

Смысл объяснений автоматика не оценивает: слово «индекс» в тексте ещё не значит, что студент понимает,
что это. Это — защита.

Папку работы сервис ищет и в корне (`lab02/`, как в практикуме), и в `pmi/lab02/`. Выбирается та,
где действительно лежит `NOTES.md`.

## Как проверять

1. Откройте попытку. Раздел **«Работа с Git»** показывает, сколько коммитов собственных, когда велась
   работа и какие сообщения неинформативны. Список коммитов — в «Технических подробностях».
2. На защите попросите **повторить шаги вживую** на новой правке: изменить файл → `git status` →
   `git diff` → `git add` → `git diff --staged` → `git commit`. Это и есть «воспроизводимая история действий».
3. Задайте вопросы из банка и поставьте 0–2 за защиту.

## Типичные проблемы

| Симптом в сервисе | Причина | Что сказать студенту |
|---|---|---|
| собственных коммитов 0, хотя в fork их видно | студент сделал `git init` внутри клона и завёл отдельную историю | пересоздать клон из fork без `init` |
| «Не удалось скачать» или «Репозиторий недоступен» | ссылка на чужой fork, опечатка или ссылка на репозиторий курса | ссылку на **свой** fork: `https://github.com/логин/CS-AI-MMCS` |
| коммитов меньше трёх | коммиты не отправлены на GitHub | `git push origin main`, затем отправить в сервис снова |
| «Коммиты сделаны через веб-интерфейс» | правили файлы кнопкой «Edit» на сайте | практика про командную строку; на защите — спросить, как это делается в терминале |
| все три изменения в одном коммите | `git add .` и один `commit` в конце | сервис засчитает один коммит; нужно три шага |
| «Сообщения коммитов неинформативны» | коммиты с сообщениями вроде `update` или `1` | сообщение говорит, что изменилось; исправить историю не нужно — учесть в следующих работах |
| автор коммитов — чужое имя | не выполнили `git config user.name` на учебном компьютере | настроить автора в своём репозитории |

## Вопросы для защиты

Видны только преподавателям. В сервисе — вкладка «Вопросы защиты» у практики и форма проверки попытки.
Базовые задайте каждому — два-три на выбор; сложные — если базовые даются легко или есть сомнения в авторстве.

### Базовые

**1. Чем сохранение файла отличается от add и commit?** · _Индекс и коммит_

> Сохранение меняет рабочую копию; add переносит изменение в индекс; commit фиксирует состояние индекса в истории.

**2. Что произойдёт, если после add снова изменить файл?** · _Индекс_

> В индексе останется версия на момент add, в рабочей копии — новая. git diff покажет разницу между ними, git diff --staged — что уйдёт в коммит.

**3. Где находится коммит до выполнения push?** · _Публикация_

> Только в локальном репозитории. На GitHub он появится после push.

**4. Как найти версию, которую вы сдаёте преподавателю?** · _Публикация_

> git rev-parse HEAD выводит полный SHA текущего коммита.

**5. Какие состояния сравнивают git diff и git diff --staged?** · _Diff_

> git diff — рабочую копию с индексом; git diff --staged — индекс с последним коммитом.

**6. Чем Git отличается от GitHub? Можно ли пользоваться Git без GitHub?** · _Git и GitHub_

> Git — программа контроля версий на компьютере, GitHub — сервис для размещения репозиториев и совместной работы. Git полностью работает и без GitHub.

**7. Что означают ??, A и M в выводе git status --short и почему буква может стоять в первой или второй колонке?** · _Состояния файлов_

> ?? — файл не отслеживается; A — новый файл добавлен в индекс; M — файл изменён. Первая колонка — состояние в индексе, вторая — в рабочей копии; MM значит, что после add файл снова правили.

**8. Вы выполнили git config user.name и user.email. Вошли ли вы этим в GitHub?** · _Автор коммитов_

> Нет: это имя и почта автора, которые записываются в коммиты. Вход в GitHub настраивается отдельно.

**9. Чем fork отличается от clone?** · _Fork и clone_

> Fork — копия репозитория на GitHub в вашем аккаунте, clone — копия репозитория на компьютере. Сначала делают fork, затем клонируют свой fork.

**10. Что такое origin и как проверить, куда уйдёт push?** · _Удалённый репозиторий_

> Имя удалённого репозитория по умолчанию. git remote -v покажет адрес — он должен вести на ваш fork, а не на репозиторий курса.

**11. Почему нельзя выполнять git init внутри склонированного репозитория?** · _Типичные ошибки_

> Появится отдельная вложенная история, не связанная с fork: коммиты не попадут в ваш репозиторий на GitHub, и сервис их не увидит.

**12. Чем плохи сообщения коммитов «update» или «1»? Предложите сообщение для своего второго коммита.** · _История_

> По ним не понять, что изменилось. Хорошее сообщение описывает изменение, например «Explain Git and GitHub».

**13. Что такое SHA коммита и почему работу удобно сдавать по нему, а не по ветке?** · _Публикация_

> Уникальный идентификатор конкретного состояния. Он указывает ровно на проверяемую версию, даже если ветка потом изменится.

**14. Покажите по git log --oneline свои три коммита. Какие коммиты в истории не ваши и откуда они?** · _История_

> Нижние коммиты унаследованы от репозитория курса при форке, верхние три — собственные.

**15. Сделайте на защите новую правку в NOTES.md и доведите её до GitHub, называя состояние файла на каждом шаге.** · _Практика на защите_

> Правка → status (изменён в рабочей копии) → diff → add (в индексе) → diff --staged → commit (в истории) → push (на GitHub).

**16. Какое состояние файла сохраняет коммит — то, что открыто в редакторе, или то, что лежит в индексе?** · _Индекс (акцент ПМИ)_

> Состояние индекса на момент commit. Правки, которые не добавлены через add, в коммит не попадают.

### Сложные

**17. git push отклонён с сообщением rejected (fetch first). Что это значит и что делать?** · _Публикация_

> На GitHub есть коммиты, которых нет локально — например, после Sync fork или правки на сайте. Сначала git pull, затем снова push.

**18. Как убрать файл из индекса после git add, не потеряв изменения в нём?** · _Индекс_

> git restore --staged <файл>: изменение вернётся в рабочую копию, в коммит оно не попадёт.

**19. Что такое HEAD?** · _История_

> Указатель на текущий коммит — обычно через текущую ветку. git rev-parse HEAD выводит его SHA.

**20. Можно ли добавить в индекс только часть изменений файла? Зачем это нужно?** · _Индекс (акцент ПМИ)_

> Да, git add -p. Так разные по смыслу правки раскладывают по отдельным коммитам, и история остаётся понятной.
