## Как сервис оценивает историю

Студент создаёт **собственный пустой репозиторий** `cs-practice` — fork репозитория курса не нужен.
Сервис скачивает его **с полной историей**. Для защиты от копирования истории вторым источником
подключается репозиторий курса [CS-AI-MMCS](https://github.com/Ekaterina0801/CS-AI-MMCS): коммиты из его
ветки `main` в собственные не засчитываются. В обычном случае все коммиты студента — собственные.

Ожидаемая история — пять коммитов: три в `main`, один в ветке `explain-branches` и коммит слияния:

```
*   Merge branch explain-branches
|\
| * Explain branches
|/
* List Git commands used
* Explain Git and GitHub
* Describe local Git states
```

| Критерий | Что проверяется |
|---|---|
| Четыре собственных коммита | коммиты студента, включая слияние; нужно не меньше четырёх |
| Объяснения в `NOTES.md` | в тексте есть рабочая папка, индекс (или staging), коммит, GitHub и ветки |
| Сообщения коммитов | не меньше 80% сообщений осмысленны: «update», «fix», «1» не считаются; слияния не учитываются |
| Ветка и слияние | в истории есть хотя бы один коммит слияния (два родителя) |
| Командная строка | коммитов через веб-интерфейс GitHub («Update NOTES.md», «Add files via upload», «Initial commit») не больше 30%. Один «Initial commit» от галочки README укладывается в допуск |

Смысл объяснений автоматика не оценивает: слово «индекс» в тексте ещё не значит, что студент понимает,
что это. Это — защита.

Папку работы сервис ищет в корне репозитория (`lab02/`) и на всякий случай в `pmi/lab02/`.
Выбирается та, где действительно лежит `NOTES.md`.

## Как проверять

1. Откройте попытку. Раздел **«Работа с Git»** показывает, сколько коммитов собственных, когда велась
   работа и какие сообщения неинформативны. Список коммитов — в «Технических подробностях».
2. На защите попросите **повторить шаги вживую** на новой правке: изменить файл → `git status` →
   `git diff` → `git add` → `git diff --staged` → `git commit`. Затем — короткий цикл с веткой:
   `git switch -c` → коммит → `git switch main` → `git merge --no-ff` → `git log --oneline --graph`.
   Это и есть «воспроизводимая история действий».
3. Задайте вопросы из банка и поставьте 0–2 за защиту.

## Типичные проблемы

| Симптом в сервисе | Причина | Что сказать студенту |
|---|---|---|
| собственных коммитов 0, хотя на GitHub их видно | студент сделал `git init` внутри клона и завёл отдельную историю | склонировать свой репозиторий заново, без `init` |
| «Не удалось скачать» или «Репозиторий недоступен» | репозиторий создан как Private, опечатка или ссылка на репозиторий курса | Settings → Change visibility → Public; ссылка на **свой** репозиторий: `https://github.com/логин/cs-practice` |
| коммитов меньше четырёх | коммиты не отправлены на GitHub | `git push`, затем отправить в сервис снова |
| «слияний в истории нет», хотя ветка была | слили без `--no-ff` — Git сделал fast-forward | ещё одна ветка с правкой и `git merge --no-ff`; на защите — спросить, что такое fast-forward |
| слияния нет, ветка есть на GitHub | ветку отправили, но не слили в `main` | `git switch main`, `git merge --no-ff ветка`, `git push` |
| первый коммит «Initial commit» | при создании репозитория отметили «Add a README» | не ошибка: один такой коммит в допуске 30%, балл не снимается |
| «Коммиты сделаны через веб-интерфейс», снят балл | правили или загружали файлы на сайте | практика про командную строку; на защите — спросить, как это делается в терминале |
| все изменения в одном коммите | `git add .` и один `commit` в конце | сервис засчитает один коммит; нужны отдельные шаги |
| «Сообщения коммитов неинформативны» | коммиты с сообщениями вроде `update` или `1` | сообщение говорит, что изменилось; исправить историю не нужно — учесть в следующих работах |
| автор коммитов — чужое имя | не выполнили `git config user.name` на учебном компьютере | настроить автора в своём репозитории |

## Вопросы для защиты

Видны только преподавателям. В сервисе — вкладка «Вопросы защиты» у практики и форма проверки попытки.
Базовые задайте каждому — два-три на выбор; сложные — если базовые даются легко или есть сомнения в авторстве.

### Базовые

**1. Чем сохранение файла отличается от add и commit?** · _Индекс и коммит_

> Сохранение меняет рабочую копию; add переносит изменение в индекс; commit фиксирует состояние индекса в истории.

**2. Что произойдёт, если после add снова изменить файл?** · _Индекс_

> В индексе останется версия на момент add, в рабочей копии — новая. git diff покажет разницу между ними, git diff --staged — что уйдёт в коммит.

**3. Где находится коммит до выполнения push?** · _Публикация_

> Только в локальном репозитории. На GitHub он появится после push.

**4. Как найти версию, которую вы сдаёте преподавателю?** · _Публикация_

> git rev-parse HEAD выводит полный SHA текущего коммита.

**5. Какие состояния сравнивают git diff и git diff --staged?** · _Diff_

> git diff — рабочую копию с индексом; git diff --staged — индекс с последним коммитом.

**6. Что такое ветка и что с ней происходит при новом коммите?** · _Ветки_

> Именованный указатель на коммит. При новом коммите текущая ветка передвигается на него, остальные остаются на месте.

**7. Почему после git switch main в NOTES.md не было раздела «Ветки»?** · _Ветки_

> switch подменяет файлы рабочей папки состоянием коммита, на который указывает main, а раздел был закоммичен только в другой ветке. После merge он появился и в main.

**8. Чем Git отличается от GitHub? Можно ли пользоваться Git без GitHub?** · _Git и GitHub_

> Git — программа контроля версий на компьютере, GitHub — сервис для размещения репозиториев и совместной работы. Git полностью работает и без GitHub.

**9. Что означают ??, A и M в выводе git status --short и почему буква может стоять в первой или второй колонке?** · _Состояния файлов_

> ?? — файл не отслеживается; A — новый файл добавлен в индекс; M — файл изменён. Первая колонка — состояние в индексе, вторая — в рабочей копии; MM значит, что после add файл снова правили.

**10. Вы выполнили git config user.name и user.email. Вошли ли вы этим в GitHub?** · _Автор коммитов_

> Нет: это имя и почта автора, которые записываются в коммиты. Вход в GitHub настраивается отдельно.

**11. Чем ваш репозиторий на GitHub отличается от его клона на компьютере?** · _Удалённый и локальный репозиторий_

> Репозиторий на GitHub — удалённая копия в вашем аккаунте, clone — локальная копия с полной историей. Они связаны через origin: коммиты попадают на GitHub только после push.

**12. Что такое origin и как проверить, куда уйдёт push?** · _Удалённый репозиторий_

> Имя удалённого репозитория по умолчанию. git remote -v покажет адрес — он должен вести на ваш репозиторий cs-practice.

**13. Почему после git clone не нужно выполнять git init?** · _Типичные ошибки_

> clone уже создал репозиторий и связал его с GitHub. Лишний init внутри него заведёт вложенную историю, не связанную с origin: коммиты не попадут на GitHub, и сервис их не увидит.

**14. Чем плохи сообщения коммитов «update» или «1»? Предложите сообщение для своего второго коммита.** · _История_

> По ним не понять, что изменилось. Хорошее сообщение описывает изменение, например «Explain Git and GitHub».

**15. Что такое SHA коммита и почему работу удобно сдавать по нему, а не по ветке?** · _Публикация_

> Уникальный идентификатор конкретного состояния. Он указывает ровно на проверяемую версию, даже если ветка потом изменится.

**16. Покажите по git log --oneline --graph свою историю. Где коммит из ветки и где слияние?** · _Ветки_

> Коммит из ветки идёт отдельной линией графа, коммит слияния соединяет её с main и имеет двух родителей.

**17. Что было бы, если слить ветку без --no-ff?** · _Ветки_

> main не менялась после создания ветки, поэтому Git просто передвинул бы её вперёд (fast-forward): коммита слияния не появилось бы, и в истории не осталось бы следа ветки.

**18. Сделайте на защите новую правку в NOTES.md и доведите её до GitHub, называя состояние файла на каждом шаге.** · _Практика на защите_

> Правка → status (изменён в рабочей копии) → diff → add (в индексе) → diff --staged → commit (в истории) → push (на GitHub).

**19. Какое состояние файла сохраняет коммит — то, что открыто в редакторе, или то, что лежит в индексе?** · _Индекс (акцент ПМИ)_

> Состояние индекса на момент commit. Правки, которые не добавлены через add, в коммит не попадают.

### Сложные

**20. Удалили ветку после слияния. Пропал ли её коммит?** · _Ветки_

> Нет: git branch -d удаляет только имя-указатель. Коммит уже входит в историю main через слияние.

**21. git push отклонён с сообщением rejected (fetch first). Что это значит и что делать?** · _Публикация_

> На GitHub есть коммиты, которых нет локально — например, после правки на сайте. Сначала git pull, затем снова push.

**22. Как убрать файл из индекса после git add, не потеряв изменения в нём?** · _Индекс_

> git restore --staged <файл>: изменение вернётся в рабочую копию, в коммит оно не попадёт.

**23. Что такое HEAD?** · _История_

> Указатель на текущий коммит — обычно через текущую ветку. git rev-parse HEAD выводит его SHA.

**24. Можно ли добавить в индекс только часть изменений файла? Зачем это нужно?** · _Индекс (акцент ПМИ)_

> Да, git add -p. Так разные по смыслу правки раскладывают по отдельным коммитам, и история остаётся понятной.
